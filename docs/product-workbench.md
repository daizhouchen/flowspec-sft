# FlowSpec 工作流方案台 · 使用说明

FlowSpec 面向需要向研发交付自动化方案、或检查 Agent 工具链的产品与开发者。它把需求整理成步骤、参数、依赖和处理策略，让人在真实接入前检查流程，并留下可恢复的方案与模拟记录。公开站使用浏览器规则和虚拟数据，不连接业务账号，也不承诺自动理解任意需求。

## 从方案到交接

### 1. 建立方案

方案库提供四个入口：

- **模板**：「客户反馈周报」「资料报告与邮件审阅」「并行分析与失败兜底」。模板中的产品、负责人、资料主题和通知目标需要逐项核对。
- **从需求开始**：输入 4–600 字需求。浏览器规则可识别部分检索、分类、摘要、报告、审批与通知组合，展示已识别内容、默认设置和未处理要求；有未处理要求时，需要确认会继续修正才能采用。
- **手动搭建**：从待补充参数的节点开始，添加工具、设置参数和依赖。方案可以保留待修正问题。
- **导入 / 恢复**：读取 WorkflowSpec JSON 或完整备份，先检查内容，再创建独立方案。导入不会覆盖同名方案。

自行运行时，「从需求开始」还可选择本地配置的编译后端。默认 Python 后端是启发式编译器；配置模型后才使用相应模型。只有选择该方式时，需求才发送给配置的 `/api/compile` 服务。公开 Pages 版本不提供这一入口。草案来源会展示，后端结果仍须经过浏览器规则检查。

### 2. 编排流程

「编排流程」展示实际依赖关系；选择节点可编辑工具参数、前置步骤、风险条件、审批、重试与失败处理。流程最多 20 个节点。修改需求说明不会自动改写节点；需要重新起草时，使用方案菜单中的对应操作，检查草案后再替换。

工具目录包含 18 个虚拟工具，覆盖检索、分类、转换、报表、审批和通知。参数编辑使用目录中的类型与必填定义。`depends_on` 表达先后关系，`input_from` 表达数据来源，后者必须指向当前节点的真正上游；多个依赖不会自动把多份数据合并。

「方案说明与触发方式」可保存手动、定时或事件声明。定时使用五段 cron，例如 `0 9 * * 1`；事件声明需要名称。工作台不运行调度器，也不监听真实事件。

### 3. 检查与修正

「检查与修正」显示结构、依赖和工具问题，可定位到对应节点。结构可读取的方案可以保存，即使仍有工具参数或依赖问题；开始试跑需要全部错误修正。

检查包括未知字段、节点编号、循环或缺失依赖、工具名、必填参数、参数类型、输入来源和受支持的条件语法。通过检查只表明符合当前规则，不证明业务要求完整、联系人正确或数据真实。模板占位值、默认假设和规则未处理的要求仍由使用者审阅。

### 4. 沙箱试跑

先选择风险等级和故障情境，再点击「开始沙箱试跑」。界面可为一个普通节点注入前 1 次失败、前 2 次失败或始终失败；每次重新试跑都会生成新的记录。风险等级来自所选情境，不是模型对真实数据的判断。

节点条件仅支持 `risk == high`、`risk != high` 等形式，右侧值可为 `high`、`medium`、`low`。条件节点必须有上游 `risk.classify`。条件不满足时跳过该节点；被跳过的控制步骤可解除后续控制依赖，但后续节点若需要读取它的输出，会因没有数据而阻断。

人工审批节点、通知工具以及显式要求审批的步骤都会等待确认。确认卡展示工具和输入或目标，选择「确认并继续模拟」或「拒绝这一步」。批准发送仍只生成模拟结果，不会发送邮件、群消息或管理员通知。独立分支可以继续；等待审批的后续步骤显示尚未尝试，失败或拒绝导致的后续步骤显示阻断。

重试次数是首次尝试之后的额外次数，最多 3 次；重试间隔只记录计划值，不实际等待。重试耗尽后才进入 `on_failure`；失败处理若是通知或审批工具，还需单独确认。处理失败通知不会把原步骤变成成功，也不会解除其下游阻断。

「逐节点结果」和完整轨迹显示输入来源、尝试次数、审批、跳过、失败与阻断原因。并行表示依赖图中的独立分支；模拟器按拓扑顺序计算，不发起并发外部调用。

### 5. 交付与记录

| 操作 | 包含内容 | 适用目的 |
|---|---|---|
| 导出工作流 JSON | 当前 WorkflowSpec 的工具、参数、依赖、触发和策略 | 交给研发继续实现；不含本机方案历史 |
| 下载完整备份 | 需求、来源说明、当前流程、版本、最近试跑快照、场景、审批决定及活动记录 | 转移浏览器、恢复继续编辑或等待确认的进度 |
| 导出交接记录 | 当前方案说明和检查结果、所选试跑的流程快照、情境、审批与重算轨迹 | 人工审阅和技术交接；Markdown 不是可恢复备份 |

完整备份恢复为新的方案 ID，保留历史、版本和有效的等待确认进度；「复制为新方案」则从 R1 开始，不带旧试跑和审批。每份方案保留最近 10 次试跑，超过上限会移除最早记录，需要长期留存时及时下载备份。

## 版本与状态

修改业务需求或工作流会增加方案版本，清除活动试跑引用并保留历史快照；只改方案名称不会增加版本。历史记录使用当时的工作流、风险情境与审批决定，不能为修改后的方案提供审批。每次新试跑都从空审批记录开始。

运行状态包括等待确认、完成、失败和无效；节点另有尚未尝试、跳过、拒绝和阻断等状态。同一运行可能同时有一个独立分支失败、另一个分支等待确认，整体此时优先显示等待确认，需结合节点结果阅读。

运行记录保存的是流程快照、情境和决定；界面和交接文件使用当前浏览器模拟器重算状态与轨迹，没有保存不可更改的执行日志或模拟器版本。它适合方案复核，不是外部系统执行凭证；未来模拟规则变化可能影响重算结果。

## 保存、冲突与恢复

方案自动保存到当前浏览器的 IndexedDB，最多 30 份。顶部会区分读取中、正在保存、已保存和修改尚未保存；只有存储事务完成才显示成功。方案含使用者输入的需求和参数，请按自身数据管理要求下载、保管或删除。

浏览器与站点来源不同，方案库也不同：公开站、本机开发端口、不同浏览器或配置文件不会自动同步。清除站点数据、隐私模式结束、浏览器配额或存储限制可能影响数据保留；完整 JSON 备份是跨环境转移和恢复的方式。

- **保存失败**：页面保留当前修改，提示重试或导出备份。先下载当前方案的完整备份，再处理存储设置，避免直接关闭页面。
- **多标签页冲突**：旧页面不会覆盖新页面已经提交的库。先备份未保存方案，再使用「载入最新本机记录」；重新载入会舍弃该页面未保存的内存修改。
- **读取失败**：界面提示重新读取，原存储不会被空方案库覆盖。
- **恢复失败**：不支持的版本、未知字段、无效工作流结构、不可达审批或超限内容会拒绝，不会静默删减后导入。完整备份上限为 2,000,000 UTF-8 字节；大方案需减少历史或拆分。

## 产品与研究边界

浏览器输出来自固定虚拟数据和选定场景，不包含真实检索、真实分类质量或真实报告内容。没有账号接入、真实工具执行、团队协作、云同步、循环流程或通用表达式求值。规则起草不支持的要求需手动补充或交给研发评估，不应把任意文字自动当成已实现步骤。

「研究与模型」保留原数据卡、模型卡和 provisional 实验结果。原 Python 模拟器主要遍历拓扑顺序并模拟显式审批节点，不能代替新版浏览器条件、重试和异常路径的验收。旧沙箱通过率、模型结构分数和训练数据规模均不能证明工作台节省了用户时间。实现细节见[工作台架构](architecture-workbench.md)，实验原文见[实验汇总](../reports/experiment-summary.md)。

## 设计参考

界面采用深色导航与浅色流程画布，以步骤、问题位置和试跑状态为中心。桌面提供依赖图与节点设置，窄屏保留表单和可滚动图。设计参考包含 [n8n 数据固定](https://docs.n8n.io/data/data-pinning/)和 [Dify 工作流调试](https://dify.ai/blog/dify-1-5-0-real-time-workflow-debugging-that-actually-works)，不据此扩展本项目的能力承诺。
